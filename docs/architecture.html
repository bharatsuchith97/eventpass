System architecture · as built

Inviteley Architecture

A multi-tenant event and QR check-in platform. All companies share one PostgreSQL database: every company-owned row carries a company_id, and every query is limited to the signed-in user's company. This sheet shows how a request is tied to one company, how companies are approved and created, how a scan becomes a check-in, and how the system is deployed.

  • React 18 · MUI · TanStack Query
  • Static landing page (no JS needed)
  • Express · TypeScript (strict) · Zod
  • PostgreSQL 17 · one shared database
  • Caddy · automatic HTTPS
  • Docker Compose on one VM

01

Deployment

Three containers on one server. Only Caddy is reachable from the internet; the app and the database talk on Docker's internal network.

Why one shared database

For the MVP it keeps deployment simple: any PostgreSQL works with no special permissions, there is one schema to migrate and one dump to back up.

How companies stay apart

The company comes only from the session, every query filters by it, and composite foreign keys stop rows of two companies from being linked. Row-level security is the next hardening step.

One port, two kinds of page

The landing page is plain HTML for search engines. Every other route gets the React shell with X-Robots-Tag: noindex, because pass and check-in links carry secret tokens.

02

How a request is tied to one company

The company is never read from the request. It comes from the session, in one lookup, and every query afterwards is filtered by it.

03

Two kinds of session

Superadmins run the platform; company users run events. They never share a cookie or a token, and a superadmin never gets access to a company's data.

04

Signup approval

Signing up only files a request. No company exists and nobody can sign in until a superadmin approves it.

05

Creating a company

What happens inside the approval transaction (approveRequest in services/platform.ts, createCompany in services/tenants.ts). If any step fails, all of them are rolled back.

StepActionTable
1Claim the request: UPDATE … SET status = 'APPROVED' WHERE id = $1 AND status = 'PENDING'company_requests
2Insert the company: ACTIVE, Starter plan, a unique slug made from its namecompanies
3Insert default settings (name, contact email, timezone from signup)company_settings
4Insert the first user as COMPANY_ADMIN, with the password hash computed at signupusers, auth_credentials
5Link the request to the new company and clear its copy of the password hashcompany_requests

After the commit the owner is emailed a sign-in link. On every boot the app applies any new migrations to the shared database.

06

QR check-in

A pass carries a random token and nothing else. Check-in looks it up by its SHA-256 hash; the token itself is stored only in encrypted form, so a copy of the database alone cannot be turned into working passes.

Showing and resending

32 random bytes become the token. Showing, downloading or re-sending a pass keeps the same QR. "Issue new QR" replaces it on purpose for a lost or shared pass, and the old QR stops working.

Guest pass page

/pass/<company-slug>/<token> needs no login. The slug identifies the company, and the lookup is limited to it. The page shows only the event and that guest's own pass, and lets them RSVP.

Manual check-in

Search by name runs the same locked transaction by ticket id. Door staff see masked email addresses only.

07

Keeping companies apart

Platform tables describe companies and logins. Company tables hold everything else, and every row carries its company's id. Keys that include company_id let the database itself refuse a row that mixes two companies.

09

Backups and restore

Every company lives in the one database, so one dump is a complete backup.

Nightly backup

deploy/backup.sh runs pg_dump into database.sql.gz, checks the dump is complete, keeps 14 days, and can copy each backup off the server with rclone (Cloudflare R2, Backblaze B2).

Restore

deploy/restore.sh <backup folder> asks you to type restore, loads the dump into the bundled database and restarts the app. Tested end to end: wipe every volume, restore, sign in, data is back.

Managed database

With DATABASE_URL pointing at Supabase, Neon or similar, use the provider's own backups instead.
